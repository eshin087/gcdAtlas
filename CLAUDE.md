## What this is

gcdatlas (https://gcdatlas.vercel.app, repo `eshin087/gcdatlas`) is a single-page WebGL2 atlas of the universe rendered entirely as ASCII characters. Real positions, distances and sizes; physically based, artistic rendering. It is meant to be a long-term project that keeps growing (more objects, an ASCII Earth, social features later) without breaking what exists.

## Golden rules

1. **Never break the build or the page.** Run `node build.mjs` (it syntax-checks the bundle) and `npm test` before every commit. Look at screenshots of anything visual you touched (`npm run shots -- key:view`).
2. **One self-contained page.** No runtime frameworks, no bundler, no external JS/CSS at runtime (Google Fonts is the only exception, and the page must still work without it). Everything is concatenated by `build.mjs`.
3. **New features ship behind a flag** (`FLAGS` in `src/04-world.js`, see `docs/FEATURE_FLAGS.md`) when they are experimental, touch the network, or could be scrapped. Default experimental flags to `false`.
4. **Performance is a feature.** Keep 60 fps on a mid-range laptop. Objects compile shaders lazily, CPU sims only run while visible (`sim` + `simActive`), far objects are single impostor dots. Never add per-frame work that scales with the total object count beyond a cheap loop.
5. **Honesty about accuracy.** Real data stays real; anything illustrative, magnified, sped up or simulated says so in its readout or fact. Update `docs/ACCURACY.md` when you add something that is not measured data.
6. **Privacy.** Nothing about the visitor leaves their device. Settings, location, collection log and daily streak live in `localStorage` under `gcdatlas.*`. The only network calls are the fonts and our own `/api/*` functions.
7. **Writing style for anything a visitor reads**: short, concrete, true sentences; no em dashes; plain words over jargon; numbers with units.

## Commands

```sh
node build.mjs                 # build dist/index.html (+ dist/artifact.html); fails on syntax errors
npm test                       # smoke test + phone layout test (tests/smoke.mjs, tests/mobile.mjs)
npm run test:mobile            # just the phone layout (390 x 844 and 844 x 390)
npm run test:tour              # long tour regression (tests/tour.mjs)
npm run shots -- sun:0,crab:1  # screenshots into tests/out/ (+ a contact sheet)
npm run catalog                # regenerate docs/CATALOG.md from the built page
npx vercel dev                 # local server with the /api functions
```

Tests need `npm install` once (dev dependencies: playwright, sharp). Headless Chromium runs WebGL through SwiftShader, which is slow: simulations run at a lower frame rate in tests, so use `__cosmos.simulate(seconds)` or step `o.update()` for deterministic checks.

## Architecture in one screen

- `build.mjs` concatenates `src/**/*.js` in rank order into one IIFE (opened in `02-core.js`, closed in `99-close.js`). Order: core (02) → GLSL (03) → world (04) → data (05) → sky/galaxies (06*) → objects (`o*.js`, then `src/objects/*`) → extras/music (07*) → camera/tours (08*) → render/UI (09*) → close (99).
- Rendering: each object is a ray-marched volume inside a bounding sphere (`prog`, drawn by `drawVolume`) and/or particle systems (`particles`). The scene renders to an HDR buffer at 2x the character grid; `FS_CELL` picks a glyph per cell; a blur adds glow; `FS_FINAL` composites glyphs. Opaque unlit cells are marked void (no glow bleeds into black hole shadows).
- Camera: focus-relative (the camera position is stored relative to the object it looks at), so light-years and metres coexist. Flights use van Wijk–Nuij paths. `SKYV` switches to the planetarium camera.
- Objects: `addObj({...})` and helpers (`addStar`, `addBody`, `addGalaxy`, `namedStar`, `addProbe`). Required: `key`, `name`, `type`, `group`, `pos` (light-years, galactic frame) or `parent`+`offset`, `rad`, `views`. See `docs/ARCHITECTURE.md` → "Object definition".
- UI state: `SET` (settings, persisted), `FLAGS` (feature flags), `tour`, `orbit`, `cam`. Test hooks on `window.__cosmos`.

## Adding content (the most common task)

1. Check `docs/CATALOG.md` (generated) and the backlog in `docs/CONTENT.md` so you do not duplicate an object.
2. Put new objects in a pack file under `src/objects/` (e.g. `p5-exoplanets.js`). Reuse shared shaders where possible; a new shader is fine but keep ray-march loops bounded (`uLod` scales steps).
3. Give every object: a true one- or two-sentence `fact`, a `readout` with a real number, 2–3 `views` (one close and dramatic), `aka` search words, and a `sortKey`.
4. Build, screenshot every view, run `npm test`, then `npm run catalog` and commit the updated `docs/CATALOG.md`.

## Workflow (see docs/SDLC.md)

- **Every version is a pull request** (`release/vX.Y.Z` into `main`, merge commit) so it can be reverted in one click. Work goes to the local folder first, then the branch is pushed. Vercel builds a preview for every PR; check it on desktop and phone before merging.
- Update `docs/CHANGELOG.md` under "Unreleased" with every user-visible change.
- `main` is always deployable; releases are tagged `vX.Y.Z` (bump `package.json`).

## Gotchas

- Do not name a local variable `P` inside object files: `P` is the global shader program registry (`P.blackhole`, `P.ptBasic`…). This has bitten before (black holes silently vanished).
- Labels show and hide with the `on` class (CSS fades them); do not set `style.visibility` on them. No other label may sit on the disc of the object you are looking at, not even its own parts (`overFocus` in `updateLabels`; in free flight the object is `cam.focus`). The owner asked for this after Sgr A*'s label covered the Galactic Centre.
- The Halo has its own camera (`shipCam` in `08-camera.js`): while riding, `updateShipCam` replaces the orbit camera, and any flight or manual input hands the camera back.
- The Halo's life is in `src/07h-halo.js` (the ship and its shader stay in `07-extras.js`): passes, light-speed legs, folds, the five jobs and their effects. While it works, `ship.viewR` / `ship.gazeR` / `ship.viewOff` / `ship.chaseOff` turn the lock-on, cockpit and chase cameras toward the job; use `o.camFrame` (not `R0`) for anything that frames the ship. It never jumps while a camera is flying up to it. Its effects are drawn camera-relative through one point, line and smoke buffer (`P_`, `L_`, `SM_`); anything near the 2.5 km ship must be kept relative to the ship (at galaxy scale a target-relative float64 is only good to ~100 km), anything on the body relative to the body. Beams are cut exactly where the body or the hull hides them (`pathLine`), and lines need about 4x the light of points to read as characters (`LK`). A light-speed hop is aimed with `aimAlign` (the exact turn after which the ship points at where the next pass starts, at up to 3 × `HALO.TURN`), re-aimed at the jump if the stop moved, and turned into a fold when it cannot be flown without a corner; the motion test fails if the heading ever turns faster than 3 × `HALO.TURN`. Tests steer it with `ship.dbg`: `reset(seed, key)` starts its route afresh with dice of its own, so it flies the same route on every run; `force`, `replan`, `skip`. Its choices (where next, how, which job, which side it banks to) draw from `hrnd()`, which is the shared `rnd()` on the site: give any new random choice in its route `hrnd()` too, or the test's route stops being fixed. Points on the hull that the jobs use are named in `HULL` (`07h-halo.js`) and must match the shader; `behindHull` / `inArm` follow its outline. `?showcase=halo` (`src/09i-showcase.js`) scripts a demo of the ship through the `TICKS` hook, with its caption in `SHOWCAP`; it holds the ship still (`S.hold`) and lights it from a fixed side (`S.light`) only while the camera circles it. `?showcase=review` (the looks review, the same file, about 45 s a round) flies Saturn, a fold to Sgr A* (Pip's probe; the chase camera, a view from above at the closest point, the plain chase view there as riders see it, the bridge), light speed to SGR 1806-20 and a fold back, in the looks the address picks. It never changes route code: it keeps `S_.force` to what the next stop asks for (`ROUTE`), starts a visit later through `S_.onFoldIn` (which `endFold` calls before the new pass is first drawn: at Saturn 16 s before the pass ends, at a black hole 6.5 s before the closest point, with Pip's launch moved to 1.8 s after the fold), and leaves a stop early from where the ship is with `leaveNow` (what `startAlign` does at a pass's end, from the ship's place now, so nothing jumps). Its buttons (teleport, black hole, Pip, light speed; keys 4 to 7) go through `press` / `tryAct`: done at once when the ship is on a pass with its hull formed, otherwise queued (one, the last pressed) and retried each tick; Pip, when out, is sent home first with `drone.hurry` (its own clock only). `end()` hands back the chase view if its own camera ('turn') was on. Its caption ends with the live shield power: `setCaption` keeps what is already typed when only the end of a caption changes (the first 8 characters must stay the same), so put anything that changes every frame last, and start captions that change part way with a fixed prefix (at a black hole the hole's name, then `PART_WORDS[SC.part]`). While a showcase writes the caption the Halo's visit and light-speed toasts are left out (`SHOWCAP.txt`), and on a phone the other toasts sit above it (`body.showcase .strip`). With it (or `?shield=`, `?fold=`, `?drone=`) the switches between the looks stack in the bottom left corner on a desk and at the top on a phone (`reviewChip` in `07-extras.js`); the fold's reloads the page, since its style is built into the shader.
- `tests/motion.mjs` opens the page with its clock fixed and its animation loop frozen (`openPage({ now, freeze })` in `tests/lib.mjs`): only `__cosmos.tick` moves anything, and nothing is drawn unless the test calls `render()`, so every run is the same. After `setDays(0)`, take one step (`tick(0)` or `view`) before anything reads planet positions (they move on the next step). `HALO_SEED=n node tests/motion.mjs` flies another Halo route, the same one every time, to hunt for or replay a bad route.
- The Halo's shader (`FS_SHIP_BODY` in `07-extras.js`) is built once per shield look (`#define SHIELD 0..3`, `BOUND`, `RM`; `shipProg(v)`, `ship.setShield(v)`, which compiles the new look in the background and swaps it in from `ship.update` once ready, `shieldSwap`; tests pass `now`). Its loops start from `ZI` (a 0 the compiler cannot see, `uM0[2].z`) and every sample of `map()` besides the march comes from one loop in `main()`: on Windows (ANGLE on Direct3D) each unrolled copy was compiled on its own and shield C took 6 s (up to 13 s in the background) to compile, long enough for Chrome to reset the GPU. Keep new loops in it on `ZI` and keep `map()` to two call sites; time a change with a D3D11 Chromium (`--use-angle=d3d11`), not SwiftShader. and the ship is drawn in a sphere `ship.drawK` times its radius so the shield is not cut off (`drawVolume(..., R*(o.drawK || 1))` in `09-render.js`). One map for its uniforms: `uP0` = (spool, light-speed sheen `S.ls`, scale, ring phase `S.ringPh`), `uP1` = (light, scoop), `uP2` = the four work lights, `uP3` = (scoop colour, heartbeat phase `S.beat`), `uP4` = (the pull's direction in world axes `S.gDir`, shield load `S.load`); `uM0` = the fold: column 0 (dissolve `S.dg`, mode `S.dm` 1 leaving / -1 arriving / 0 whole, the heart's flare `S.hfl`), column 1 (the shield's share `S.shK`, style amount `S.sx`, collapse clock `S.cc`), column 2 (cell size `S.cs`, B's dark-heart growth `S.sy`). The heart's own glow is capped at `min(power, 2.2)` (it must never become a white ball); extra power goes to the rings, chains and shield. The ring phase and the beat are integrated in `shieldUpdate` (07h-halo.js), never computed from `uTime` (which counts from page load: speed x time made the rings whip round). The load comes from the real escape speed (`escapeAt`, `VESC`); `isHoleTarget(tg)` is the one test for a black hole. `S.gWant` is the load the pull where the ship is asks for; the readout and the showcase show `shieldPower()` (never more than that, none at light speed), so a load still fading from the last stop is never put down to the next one. The shader cuts the load at light speed (`ls`). Shield A's line is the ray's closest pass by the hull over its whole length (`am`, refined between march steps) at `DL`, about a pixel wide at any size; C (crystal: `crystal()`, the nearest of nine scattered points on a grid stretched along the ship, one `ZI` loop, edges two pixels wide) has the same line, scaled by the load (none at rest), because its facets alone do not flare on a small or edge-on ship; only B's bubble reaches past the hull's own sphere (`SHIELD_BOUND`). Its fine detail fades with the ship's size on screen (`sv`); the one-pixel flare line (A, C) and B's rim flare show at any size. Nothing is damped for the bridge as a whole: each term fades out only near the camera, by its distance along the ray (`smoothstep(0.1, 0.4, t)`). Skip the shield's per-pixel work while it is folded away (`shk`).
- The fold's look (`?fold=a|b|c`, `foldLook` in `07-extras.js`, compiled in as `#define FOLD`; the rest in `07h-halo.js` from `FLK` on). The hull breaks up into square cells in the ship's plane: `thrC` in the shader and `foldCellThr` in JS give each cell the same threshold (the same `foldF` front and the same integer hash): change both together, or embers leave from cells the shader has not cut. The cut is part of `map()` (`cellD`, a distance bound over the 3 x 3 cells round a point), so the shield's outline crumbles with the hull. It runs on its own clocks (`S.fk` to the jump, `S.asm` from the arrival), never the route's: `HALO.FOLD_T` stays 0.4. Embers are pure functions of those clocks (`emberAt`), drawn about one per character of the ship on screen (`keep` in `foldDraw`); their randomness is `lcg`, never `hrnd`. Behind the hull use `emberHidden` for them (the bow's rough ellipsoid in `behindHull` hides embers lifting off it). `behindHull` and `liveCell` only count cells still there during a fold. The cell size is one of `CS_STEPS` (the nearest to a character on screen, `foldCs`), and their tables are built in spare time after start-up (`cellTable`): building one inside a tick took up to 4 ms. The hash needs `precision highp int` (added in `shipProg`). Riding along, the chase camera moves in to `S.fz` (0.6) of its distance during a fold, and for fold C also swings round the ship to the side `S.fsd` by `S.fs` (its thread runs straight ahead, end-on from behind); both in `shipPose` in `08-camera.js`, framing only. `endFold` leaves the ship at full size (`S.emerge = 1`): the hull forms cell by cell, and anything placed on the ship from JS (`toShip`, `shipPt`) assumes full size.
- Pip, the Halo's drone (`src/07i-drone.js`; it must sort after `07h-halo.js`, whose `S_`, `HULL` and `ACT` it uses): a volume of its own (`P.drone`, one program per look, `#define LOOK 1..3`, `?drone=a|b|c`), drawn from `ship.drawAfter` right after the ship's volume (the two overlap, and volumes are only sorted by their centres) and hidden, never half-drawn, where the hull or the body is in front of it (`pipHidden`); the object itself stays `hidden` so the render loop never draws it a second time. Its controller is `drone.ctl`, run once a tick after the camera has moved (`AFTER_CAM`, declared in `04-world.js`, run by `tick` before every object's `rel`): its spot is picked in the camera's view, and worked out from the camera's last place it shook with uneven frames. It keeps to that spot on a critically damped spring (`pipAnchor`: `anc`, `ancV`), so a moving or new spot never makes it jump; everything else it does is a smooth function of its clock `u`, and flights far away keep an even pace on screen (`pipFly`). The probe job (`ACT.probe`) only keeps time; the timeline is `PT` (launch at `tA + 0.3`, back aboard 11.9 s later, so the route is unchanged): it streams out of the bay as embers and takes shape (`ASM0` to `ASM`), opens its eye, waves hello, spins, peeks, works (`PIP_ACTS`: pictures with a hop, the loop, looking back at the ship, near a hole a goodbye), then breaks up into embers that stream into the bay (`DIS0` to `DIS`). The break-up is cells in its own frame (`pipTable`, cubes about a character on screen, `PIP_CS`): `thrP` in its shader and `pipCellThr` in JS give each the same threshold (change both together), and `emberPip` is a pure function of the clock. Its dice are `lcg(seed)`, heights use `surfDrawn`, and its uniforms are `uP0` = (eye open, iris glow, thruster, mood), `uP1` = (light, unfold), `uP2` = (pupil x, z, antenna wink, lens lamp), `uP3` = (iris colour, how much of it is there), `uM0` columns: 0 = (scale, B's ring phase, C's tail), 1 = (dissolve, mode, cell size), 2 = the way to the bay in its own frame. Tests read `ship.dbg.drone` (`state`, with `shows` from geometry, `pres` and `embIn` for the break-up, and `pose` to hold it still for screenshots) and `ship.dbg.surfDrawn`. Near a black hole or a magnetar (`pipKind` 'near') Pip works at its hello spot for the whole job (`pipWork`), a spot in the camera's view picked clear of the hull and off the hole's disc (`pipHello`); `drone.reframe()` picks a new one for a new view (the bridge, the showcase's view from above) and Pip glides there on its spring. That spot is outside every shield, so never say Pip is inside the shield, and give no physical reason for it staying by the ship (at 27 to 31 r_s it would not be captured). `drone.reset` puts all of `PIP` back as on page load (`pipFresh`).
- Objects added after start-up need a label element (`labelEls[o.index]`) because labels are created once at init.
- `afterFrame` (in `09-render.js`) runs once right after a frame is drawn; use it to read the canvas (photo mode).
- WebGL points/lines are not depth-tested against volumes. Black holes are handled for every particle system (`uHole` in `particleVS`); for other opaque bodies hide what should be behind them in the vertex shader (see the satellites in `src/objects/e1-earth-live.js`).
- A volume is only drawn inside the screen rectangle around its bounding sphere (`rad`). Anything a shader draws beyond `rad` gets cut along that rectangle, which moves with the camera: fade effects out before they reach the bound (see the Sun's coronal mass ejections).
- Long flights go through `flyTo` (one flight that may bend past a real object in view, `scenicWaypoint` / `passBy`; never a separate leg to it); tests should wait with `__cosmos.land()`, not a fixed flight duration. Objects that should never be passed set `noWaypoint`.
- GLSL reserved words (`patch`, `sample`, `input`, `output`, `filter`, `active`…) fail only at shader compile time, which is lazy: name variables plainly and screenshot the object after any shader edit.
- A lost WebGL context (a driver reset, Chrome's GPU watchdog) stops drawing, shows a line in `#nogl` and reloads the page when the context comes back (`webglcontextlost` / `webglcontextrestored` in `09-render.js`); `progReady` returns false while it is lost.
- A volume shader can take a second texture: set `tex2:'name'` on the object and declare `uniform sampler2D uTex2;` in its shader (bound to unit 7; Earth's night lights use it).
- Do not give an object a property the engine sets itself: `mag` (on-screen enlargement), `vis`, `pvis`, `rpx`, `rel`, `dist`, `magHide`. A matrix in `mag` once made the Crab vanish; the smoke test now checks.
- In the Solar System overview bodies are enlarged (`SYSMAG`, `o.mag`); use `o.rad*magOf(o)` for anything drawn or picked on screen, and `o.rad` for physics. Inner planets can be hidden there (`o.magHide`) when the enlarged Sun covers their orbit.
- Picked objects play their views in a loop (`show` in `08-camera.js`); give every object views that work one after another, not only as tour stops.
- The artifact build (`dist/artifact.html`) runs without `/api`, so live features must degrade gracefully.
- `setBasis` turns the view by `viewShift` (phones: frame the object in the free space) plus `leash` (a two-finger slide on a touch screen, which keeps the lock; it eases back when play, a tour or a flight takes over). So the locked object is not always in the middle of the screen: project with `projectCSS`, never assume the centre. On a desk a right-drag still lets go (`letGo`, which remembers `freeFrom`); the free camera then moves with `freeFrom` while near it (`anchorObject` in `refocus`), and play / the back pill (`backTarget`, `goBack`) fly back to it. Home is `goHome` (button, logo, H, Home key); help is on ?.
- The desk top bar has a forced row break (`.controls::after`, order 7): travel and play / pause (order 8 and 10) always sit on the second row, so the play button's changing words never move the top row. New top-bar buttons keep order 0; check the bar at 1280 px. There is no separate resume tour button (0.8.5): the green button beside the name (`#goNext`, `goNextState` / `syncGoNext` in `09-render.js`) says where it goes, and the angle arrows (`#prevObj` / `#nextObj`) live on the angle line (`#progress.angles`).
- A tour plays `tourViews(o)` (08-camera.js): all of an object's views, unless it lists fewer in `tourViews` (Earth plays three). `tour.view` is still an index into `o.views`; a swing's target is `tour.to` / `show.to`, so taps during a swing count from where the camera is heading. Check new or changed views on a desk and a phone: angles that look empty are bugs.
- Esc goes through `closeOpen()` (09-render.js): anything new that opens like a panel should close there before the camera lets go. On a touch screen only taps on the canvas and labels are eaten while the interface is faded (09h-ui.js); faded buttons work on the first tap. The faded scale bar track lets touches through to the sky (`body.ui-idle .lad-track` in `00-head.html`), so a tap there on a tablet only wakes the interface. Keys typed into an input stay there, except Esc.
- Phones get their own layout (dock, info card, scale chip; `src/09h-ui.js`). The breakpoint is `COMPACT_MQ` in `src/04-world.js` and the matching `@media` blocks at the end of `00-head.html`; change both together. Anything new that sits at the bottom of the screen on a phone should stack above `var(--dock-h)` + `var(--sheet-h)`, and anything that should fade when idle goes in the `body.ui-idle` rule.
